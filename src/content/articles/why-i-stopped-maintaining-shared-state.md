> **TL;DR:** My coding agents were repeatedly trimming the shared overview used to continue work between sessions. I separated history, workstream records, and the startup view generated by code. A five-week scan across five state files found five non-merge commits with reductions above 300 bytes, each 302–307 bytes. The early evaluation still missed its reading and commit targets.

## The fallback that became routine work

I built **SystemPrinter**, an **Agentic Software Engineering Production System**, to coordinate coding sessions across several machines. Work outlives sessions: context fills up, a terminal closes, or a task continues elsewhere. The successor needs to know what happened and what to do next.

My first approach was straightforward: keep a shared Markdown document current and make the next session read it.

In September 2026, a size gate in the workflow forced **25 reduction commits on the shared state file in one week**, seventeen of them in two days.

That gate was supposed to be an emergency fallback. Instead, maintaining the system's memory had become recurring work for the agents using it.

## One document was doing three different jobs

The initial structure combined current state, open threads, and a separate decision log. Per-machine state files followed, but a shared overview remained. Over time, those files accumulated historical accounts, ongoing workstream status, and instructions for successor sessions.

Those have different lifecycles. **History should remain available. Current status should be replaceable. Startup context should be selective.** I had asked the agents to reconcile all three by editing prose.

Removal rules existed, but conflicted with size targets and were not reliably implemented. Then the shutdown command made it worse: it appended the session's full closing account to the machine's current-state file, although I had decided to archive it. The outgoing session cleaned up by hand, with three compressions within three hours. The machinery was producing its own maintenance work.

I introduced session journals and removed the advisory layer in one rollout, first on one machine, then across the fleet. The hard gate remained, and the reported burst of cuts followed within days. Adding journals had not yet removed the accumulated-state maintenance problem.

Progress notes remained useful. Anthropic's work on long-running agents also uses progress artifacts and Git history to connect sessions. [1] My problem was combining historical storage, current state, and mandatory startup reading.

## Move mechanics out of the model loop

An earlier change had already addressed shutdown. By late July, the procedure had drifted to **21 steps across three documents**. Two inspected shutdowns took roughly 15 and 10 model turns. The first read approximately **3.7–4.0 million tokens** from cache, roughly half of them through forced compression, and 11 of its tool steps were pure mechanics.

Deciding what remained unresolved required judgment. Appending records, releasing claims, staging files, synchronizing the repository, and checking results could run as a deterministic sequence.

At the end of July, I moved those mechanics into one command, with a preview mode and explicit stop conditions. The model still prepared the account and continuation information.

The early-September journal redesign was followed by a median preparation time of **4 minutes 3 seconds across 61 shutdowns**, versus **10 minutes 13 seconds in one baseline session**. The command already existed in that baseline. Preparation ended at its first real invocation, so the comparison measured neither the command's introduction nor the complete handover.

## Separate history, continuation, and presentation

The intermediate journal design still depended on another model role to distribute its contents, leaving another delivery step to trigger and monitor.

The late-September redesign reframed the question: why should any agent maintain that accumulated document at all?

I introduced the redesign on one machine, then across the fleet within days. It separated three responsibilities.

### Session journal: preserve the account

Journals remain available after processing without becoming mandatory full-text input to successors. The shutdown path appends accounts to journals, normally organized by session.

Code rejects a blank account and warns about a missing one. The shutdown code only appends, but nothing blocks ordinary edits to old entries.

### Continuation record: replace the current position

A session and a workstream are different units: one session can touch several streams, and one stream can continue across sessions.

Each machine and workstream gets a continuation record describing its latest position. Accepted writes replace that record. On normal shutdown, code also tries to copy the text into the journal, whether accepted or rejected, but that copy is not guaranteed.

The record has five fixed sections:

```text
Intent     Purpose and intended end state.
Status     Established facts and remaining uncertainty.
Next step  The first concrete action for the successor.
If-then    Conditions that change what should happen next.
Evidence   Pointers supporting important claims.
```

During normal shutdown, the model supplies content and selects the initial workstream; other commands can also write records. Code validates structure, allowed status, ownership, and size, then stamps the session identifier and time. The body is capped at **4,000 Unicode code points**, including headings.

Validation enforces format, not factual truth, resolvable evidence pointers, or useful next steps.

### Generated startup view: select what the successor sees

At startup, code assembles the selected record, summaries of other workstreams, pending items, information about other machines, this machine's claims, approval gates, and commits naming this machine.

The report is printed, not committed. Journal metadata helps select continuation and identify pending work; full journal history is excluded.

Agents no longer maintain the accumulated overview. Code still writes a small per-machine shared summary.

This resembles CQRS's separation of read and write models. [2]

## What the measurements actually show

I kept the redesign because it removed recurring overview maintenance from the agents. The early evaluation missed its reading and commit-count targets, but found no cuts under its bookkeeping filter on the migrated machine.

### Follow-up across the fleet

A later five-week scan covered **all non-merge commits across the five state files**. It began after the final fleet migration on **October 1** and ended on **November 5**. Only **five commits** reduced a file by more than 300 bytes. All five were shutdown commits on the shared file, each removing **302–307 bytes**—a pattern consistent with replacing generated blocks.

At the end of the scan, the shared summary was **1,653 bytes**, excluding journals and other startup inputs.

### Initial evaluation on one machine

The original evaluation compared **15 startup sessions and 40 shutdowns before** with **16 startup sessions and 17 shutdowns afterward**, on one machine. Repository history covered 14 days before and approximately two days after; model mix also changed.

| Measure | Before | After | What it measures |
| --- | ---: | ---: | --- |
| State-file cut commits under the evaluated machine's bookkeeping filter | 28 | 0 | Filtered maintenance events; unequal windows |
| Recorded handover text before the first work step, median | 33,877 characters | 20,020 characters | Reading volume; lower bounds |
| Bookkeeping commits per shutdown, median | 4 | 2 | Repository administration per shutdown |
| Context at the first work step, median | 123,563 tokens | 115,342 tokens | Context size at the chosen cut point |

A cut counted only for the evaluated machine's own bookkeeping commits that removed more than 300 bytes. Other machines still compressed state during that window.

The reading count missed some combined reads; with them included, the after median is **20,878 characters**. Either way it missed both targets, 16,938 and 8,000 characters. The commit target of at most one was also missed.

Sixteen of 17 terminations had records valid at their own commits. The remaining session had no shutdown commit; how it ended is undocumented.

The earlier sample already carried a median **59,318 tokens at its first assistant turn**, before measured handover reads. Shrinking state cannot remove those existing inputs.

## Failure modes that remained

**Partial failure and unsafe retries.** In one recent shutdown, two independent problems occurred: record validation failed, and a repository check blocked the push. Rerunning to resubmit the record duplicated the shutdown account and sent a second owner notification. Recovery required manual work. The duplication defect was still open at the end of this study, and record rejection did not itself halt a requested machine shutdown. Duplicate side effects are a related concern in AWS's treatment of idempotent APIs. [3]

**Incorrect state selection.** A read-only recomputation found hexadecimal identifiers falling through to filename ordering where numeric ordering was expected, selecting an earlier shutdown. The defect was still open at the end of this study.

**Unexpected termination.** A journal exists after interruption only if something was written earlier. Pending work may be flagged while startup still presents an older session's record. The latest intent is not guaranteed to survive.

**Remaining shared-state conflicts.** A shared-header merge conflict occurred during this study. Narrower ownership had not eliminated every collision.

Moving work into deterministic code created software that also needed maintenance.

## Evidence scope

This case study covers one owner-operated system through **November 5, 2026**. The observational measurements were often model-assisted; the subsequent technical audit reproduced the central comparison from recovered raw data. Shutdown evidence covers two sessions, with a full token analysis for one; the preparation baseline is one session. Unequal windows, changing model and session mixes, and instrument changes limit comparisons. The opening count of 25 is a fleet-wide figure from the time; its counting rule was not preserved.

The first-work boundary was a file-writing tool call or non-routing subagent call, not an assessment of useful work. Task quality, human intervention, total transition cost, and productive resumption were not systematically measured. Maintenance counts, preparation time, and context size do not establish end-to-end productivity; valid records and retained journals do not establish lossless continuity.

## Engineering lessons

**Separate retention from startup context.** History can remain available without becoming mandatory input. Preservation and selection need different policies.

**Let models write bounded continuation records; let code enforce mechanical rules.** Structure, metadata, ownership, and presentation need not depend on an agent maintaining accumulated prose.

**Test retries and interruption separately.** Successful ordinary shutdowns say little about partial writes, rejected records, or sessions that end before writing.

The change I would repeat is specific: **preserve what the agent knows, constrain what it must write, and generate what the successor needs to see.**
